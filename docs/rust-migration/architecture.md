# Rust migration architecture

Status: implemented product architecture; physical validation pending

## Dependency direction

```text
firmware composition
  -> board module + ESP-IDF adapters
  -> application ports
  -> TONEX ONE application
  -> TONEX ONE domain and protocol
```

Dependencies may only point downward. Domain and protocol crates must build
and test on a desktop host and must not import ESP-IDF, FreeRTOS, LVGL, board
names, or GPIO numbers.

## State ownership

`AppController` is the sole mutable owner of application state. Every
producer converts external activity into a typed `AppCommand`:

- USB connection and parsed messages
- footswitch events
- MIDI input
- touch/UI actions
- optional web commands

Handling a command returns an `AppEffect`. Platform composition executes the
effect through a port and feeds any result back as another command. Read
consumers receive an `AppSnapshot`; no API exposes a mutable internal pointer
or a lock whose release is delegated to the caller.

## USB boundary

The ESP-IDF USB Host and CDC-ACM implementation remains below a narrow
transport port for the first stable firmware. It owns enumeration, CDC
handles, transfer buffers, and callback context. It does not parse TONEX ONE
messages.

The callback contract is:

1. validate the pointer and length against the configured receive buffer;
2. copy bytes into a bounded owned queue;
3. record overflow explicitly;
4. return without blocking, parsing, logging large buffers, touching the UI,
   or modifying application state.

Rust framing and message parsing run outside the callback context.

## Board composition

A board module contains only verified hardware composition:

- pins and buses;
- flash and PSRAM requirements;
- reusable display/touch/I/O/LED driver selection;
- display geometry and rotation;
- capability declaration;
- partition requirements.

It does not contain TONEX ONE behavior. Unsupported hardware is represented
by zero-cost `NoDisplay`, `NoTouch`, `NoLeds`, or `NoSwitches`
implementations rather than heap-allocated optional trait objects.

Board selection is compile-time and exactly one board feature must be active
for a firmware build. The host registry is metadata plus compile evidence; it
does not claim physical validation.

## Unified display and Web presentation

`tonex-ui-model` derives a `ToneProfile` from verified preset data without
storing a per-preset skin index. Explicit ASCII keywords in the synchronized
preset name take precedence; model gain is used only as a clean/neutral/modern
fallback when the name contains no recognized model evidence. The classifier
is deterministic, allocation-free, hardware-independent, and unit tested.

The available TONEX ONE fixtures expose a user preset name and model
parameters, but no verified manufacturer or exact amplifier-model identifier.
The profile is therefore a visual category, not a claim that the firmware has
identified the captured amplifier. If future physical packet evidence exposes
an exact model identifier, its mapping belongs in this classifier rather than
in display, Web, or board code.

The RGB565 board renderer and embedded Web UI share the same warm dark
surfaces, semantic profile names, profile accent palette, and visual hierarchy:
accented preset number, preset name and tone family, amp-face metrics, A/B/C
slot selection, then contextual slot/preset navigation. Configuration stays visually
secondary so the Web page reads as the same controller rather than an
administrative console. Board render previews are generated by:

```powershell
cargo run -p tonex-ui-renderer --example render_preview -- .\artifacts\ui-previews
```

## Safety policy

Core crates forbid unsafe code. Future unsafe code is allowed only in
dedicated ESP-IDF FFI or DMA modules. Every unsafe block must document:

- pointer provenance and alignment;
- valid length and allocation;
- ownership and lifetime;
- callback thread/task context;
- aliasing and synchronization guarantees;
- which C API contract establishes those guarantees.
